# study-note-deploy-system-admin

운영자 한 명이 배포 이력 · 로그 · 서비스 상태 · 로그인 시도 기록을 읽기 전용으로 보는 어드민 화면(Next.js 15 App Router).
어드민 백엔드는 따로 두지 않는다 — 이 앱의 서버 쪽 코드가 master · 관측 · 알림 · backend 서버를 직접 부른다.
지금 있는 것: 로그인(`/login`) · 로그인 뒤 홈(`/`, 화면 넷의 메뉴) · 화면 넷(`/deploys` · `/logs` · `/status` · `/login-attempts`) · `POST /api/auth/login` · `POST /api/auth/logout` · `GET /api/health` · 화면 넷과 두 상세의 데이터 경로(아래 "구성") · Claude 사용량(`/claude-usage` — 아래 "Claude 사용량") · 주인 표시(`/owner-mark` — 아래 "주인 표시").

## 구성

- `src/middleware.ts` — 공통 진입. 세션 없는 화면 요청은 `ADMIN_ORIGIN` 기준의 `/login` 으로 307(Next 15.5 middleware 는 상대 Location 을 받지 못한다 — 내부 호스트 이름 대신 설정값을 쓰고, nginx 의 `proxy_redirect` + `absolute_redirect off` 가 바깥으로는 `Location: /login` 으로 바꾼다). **기본 거절**: `classifyPath`(`src/features/auth/lib/auth-boundary.ts`)가 public 이라고 한 경로(`/login` · `/api/auth/login` · `/api/health` · `/favicon.ico` · `/_next/static/…`)만 세션 없이 통과. 나머지는 서명한 세션 쿠키가 없으면 화면은 `/login` 으로(307), `/api/…` 는 401. 런타임은 Node.js(`config.runtime = "nodejs"`, Next 15.5 stable) — 세션 검증이 `node:crypto` HMAC 을 쓴다. argon2 · ioredis 는 임포트하지 않는다.
- `src/features/auth/server/require-session.ts` — 두 번째 겹. 보호 화면은 `requireSession()`(없으면 `/login`), 데이터 경로는 `requireApiSession()`(없으면 401)을 **직접** 호출한다. 새 화면·경로·다른 서버를 부르는 서버 쪽 함수도 반드시 호출한다.
- `src/features/auth/lib/` — 세션(HMAC-SHA256, 12시간, 연장 없음) · 자격(argon2id, ID 가 틀려도 더미 해시로 같은 검증) · Origin(설정값과 글자까지 같음) · 속도 제한(IP 마다 60초 10회, 자리별 메모리) · 관측 서버 판정 · 임시 제한(관측 서버 장애 시 3회 → 15분) · 대기열(상한 500, 복귀 뒤 `replayed:true`) · 잠금 알림.
- `src/features/auth/server/login-service.ts` — 속도 제한 · 임시 제한 · 대기열을 프로세스 안에 하나만 둔다(`globalThis`).
- 화면 넷과 두 상세(배포 상세 · 연관 로그)의 데이터 계층 `src/features/{deploys,logs,status,login-attempts,deploy-detail,log-trace}/` — `lib/`(순수: 입력 검증 · 다른 서버 클라이언트 · 응답에서 화면에 필요한 칸만 고르기, 설정·Next 를 읽지 않는다) + `server/`(진입 함수 — `requireSession()`/`requireApiSession()` 을 **직접** 부른 뒤에만 설정을 읽고 다른 서버를 부른다) + `ui/`(서버 컴포넌트 — 받은 값만 그린다. server · `*-client` · 설정을 값으로 임포트하지 않는다). `src/app` 의 화면 · `GET /api/{deploys,logs,status,login-attempts}` · `GET /api/deploys/detail` · `GET /api/logs/trace` 는 진입 함수만 부른다(화면 넷의 기능 폴더는 소스 검사 `src/app/screen-data-imports.test.ts`).
  - 다른 서버 호출: 전부 GET · `redirect: "manual"` · 본문까지 5초 기한. 실패는 고정된 짧은 사유(`src/shared/lib/upstream-result.ts`)와 상태 코드만 — 오류 본문 원문 · 주소 · 예외 문구는 넘기지 않는다. 정상 응답 안의 사유 글자(감시 대상의 DOWN 사유 · backend 의존성 detail · 관측 서버 헬스의 failure)는 주소를 `(주소)` 로 가리고 120자로 자른다(`maskUpstreamReason`). 입력이 틀리면 데이터 경로는 422 `invalid_input`(다른 서버를 부르지 않는다), 다른 서버가 실패해도 200 에 그 칸의 실패로 보인다. 상태 화면의 다섯 호출은 병렬.
  - 화면 넷: 배포 이력(`/deploys` — 줄을 누르면 오른쪽에 배포 상세(`deploy-detail`, `GET /api/deploys/detail`): 요약 · 직전 성공 배포→이번 배포의 커밋 목록 · PR · 커밋별 바뀐 파일과 diff. 커밋 목록 · diff 는 배포 master 의 git 조회(`GET /deploys/git/commits` · `GET /deploys/git/commit` — 배포 이력과 같은 `DEPLOY_MASTER_URL` · `DEPLOY_SECRET`)에서, PR 제목 · 본문만 GitHub 에서 읽는다. 선택은 주소의 `selected` · `selectedService` · `commit`) · 로그 조회(`/logs` — 줄을 누르면 오른쪽에 연관 로그(`log-trace`, `GET /api/logs/trace`): 고른 로그 · 이 요청 요약 · 같은 요청 ID 의 연관 로그 · 그때 서버 상태(수준별 건수 · 배포 · 알림). 선택은 주소의 `selected`) · 상태 한눈에(`/status`) · 로그인 시도 기록(`/login-attempts`). 공통 틀 `src/features/admin-shell/ui/AdminShell.tsx`(내비게이션 · 로그아웃 · "임시 제한 중").
- 문제(`/incidents` · `GET /api/incidents`, `src/features/incidents/` — `lib/` · `server/` · `ui/` 의 나눔은 위와 같다) — 지금 열려 있는 문제의 목록과, 고른 문제(`?incident=<식별자>`) 하나의 근거 묶음. **읽기 전용**이다(폼 · 단추 · 스크립트 없음 — 고르기 · 이동은 링크). 조치(되돌리기 · 다시 배포)도 재배포의 확인 화면으로 가는 링크다(아래 "재배포 접수"의 문제의 조치).
  - 보이는 것: 목록은 문제마다 종류 · 대상 · 언제부터 · 심한 정도(글자로 — 색만으로 전하지 않는다). 근거 묶음은 구역 다섯 — 무엇이 · 언제부터 / 관련 알림 / 로그(경고 · 오류, 최근 100줄 — 넘으면 "더 있음"을 적는다) / 배포(배포 실패는 앞 성공 배포와의 사이의 커밋, 그 밖은 앞 1시간의 배포) / 자원(그 서비스가 그때 있던 서버의 값 — 로그 추적의 자원 칸, 자원 임계값은 그 서버의 지금 값). 로그 줄 · 배포 · 서버는 로그 화면 · 배포 이력 · 서버 자원 화면의 그것으로 가는 링크.
  - 출처 넷: 감시 대상 DOWN(알림 서버 `GET /monitors`) · 자원 임계값(관측 서버 `GET /metrics/latest` 의 firing) · 서비스의 가장 최근 배포가 실패(배포 master `GET /deploys?limit=200` — 그 뒤에 성공했거나 다시 배포하는 중이면 열린 문제가 아니다) · 오류 로그(관측 서버 `GET /logs?level=error`, 최근 10분의 줄을 서비스마다 센 수 — 급증 판정은 하지 않는다). 한 출처 · 한 칸의 실패는 그 출처 · 그 칸만 "확인하지 못함"으로 보이고 나머지는 그대로 보인다. 로그인 잠금은 문제로 치지 않는다.
  - 호출 수: 목록 네 호출(한꺼번에, 각 5초) + 근거 묶음 16 이하(알림 기록 1 · 로그 2 · 커밋 1 · 자원 칸 13 가운데 그 종류가 쓰는 것 — 한꺼번에, 자원 칸은 전체 8초 상한). 근거 묶음은 목록이 받은 배포 이력 · 최신 지표를 다시 거른다. 새 조회 경로는 없다 — 기존 클라이언트를 그대로 쓴다.
  - 근거 묶음의 글(응답의 `selected.text` — 분석은 이것을 가린 뒤에 다시 자른다: 아래 "문제의 분석")은 화면과 같은 묶음에서 만든다. 48,000바이트를 넘으면 값 하나를 500자로 → 오래된 로그 줄(10줄까지) → 한 줄의 글 1,000자 → 오래된 알림 → 커밋 → 남은 로그 줄 차례로 줄이고, 그래도 넘으면 끝을 잘라 맞춘다. 줄인 것을 화면과 글의 "줄인 것"에 적는다.
  - 다른 서버에서 온 글자는 글의 줄 구조(`# 문제:` · `## ` 구역)를 꾸며 낼 수 없다 — 한 줄짜리 값의 줄 끝 · 제어 문자는 빈칸으로, 로그의 글은 이어지는 줄마다 앞에 `| `. 화면은 받은 글자 그대로(이스케이프).
  - 목록은 덮지 못한 범위를 한 값(`uncovered`)으로 모아 적는다 — 출처 실패 · 오류 로그 500건 상한 · 상태를 아직 모르는 감시 대상 · 배포 이력 200건 안에 보이지 않은 서비스. 그런 범위가 있으면 빈 목록의 말은 "확인된 범위에서는 열린 문제가 없습니다". 목록에 없는 문제를 고르면 같은 값을 읽어, 그 범위에 들면 "확인하지 못했습니다", 범위를 실제로 확인했을 때만 "지금 열려 있지 않습니다"(해시 꼴 배포 식별자는 보이지 않은 서비스가 하나라도 있으면 확인하지 못함).
  - 알고 두는 한계: 관련 알림은 알림 서버의 최근 200건 안에서만 찾는다(창의 앞쪽에 닿지 못하면 그렇다고 적는다) · 관측 서버가 111자를 넘는 알림 열쇠를 해시로 줄이면 자원 임계값의 관련 알림이 짝지어지지 않는다 · 감시 대상 → 서비스의 대응 표(`lib/monitor-services.ts`)에 없는 대상(배포 master · agent)은 로그 · 자원을 "대응 표에 없음"으로 둔다(짐작하지 않는다) · 배포 실패의 전체 출력은 이 화면에는 싣지 않는다(분석의 보낼 글에만) · 같은 대상이 닫혔다 다시 열려도 식별자는 같다. 상태 화면의 DOWN 인 감시 대상 줄과 울리는 임계값 칸에서 이 화면의 그 문제로 간다(상태 화면에는 배포 이력이 없어 실패한 배포의 링크는 없다).
- 문제의 분석(`/incidents/analysis?incident=<식별자>` · `POST /api/incidents/analysis`, `src/features/incident-analysis/`) — 아래 "문제의 분석".
- `src/shared/config/server-config.ts` — 환경 변수를 읽는 유일한 곳(`server-only`).
- `src/shared/lib/logger.ts` — `requestId:admin:message` 한 줄, stdout + Redis 스트림 `logs`(실패 무해). IP · 입력 ID · 비밀번호 · User-Agent 는 넘기지 않는다.

## 임포트 정책

**절대경로(`@/...`)만 사용한다** — 같은 폴더 안이라도 상대 임포트 금지(front 와 같은 정책).

## 실행

- 테스트: `npm test` · 빌드: `npm run build && sh scripts/check-client-bundle.sh`(브라우저로 가는 `.next/static` 에 비밀값 이름·테스트용 비밀값이 없는지 검색 — Docker build 단계에서도 돈다).
- 무중단 배포 구성(앱은 두 자리 `admin-blue`·`admin-green` 중 하나만 뜨고 nginx 가 18000 을 받는다). `.env` 작성(`.env.example` 참고) 후:

  ```sh
  mkdir -p deploy/active
  cp deploy/nginx/nginx.conf deploy/active/nginx.conf
  cp deploy/nginx/upstream-blue.conf deploy/active/upstream.conf
  cp deploy/nginx/edge-allow.conf.example deploy/active/edge-allow.conf   # 주소를 실제 엣지 IP 로 바꾼다
  docker compose up -d --build admin-blue nginx
  curl -sD- -o /dev/null http://<BIND_ADDR>:18000/api/health | grep -i x-deploy-slot
  ```

  - nginx: 로그인 경로(`location = /api/auth/login`)는 본문을 모으지 않고 앱으로 흘려보낸다(`proxy_request_buffering off`). 그래서 앱의 4KB 상한과 **전체 3초 기한**이 nginx 를 거쳐도 실제로 걸린다(넘으면 400 `malformed` 로 기록되고 속도 제한에도 든다). nginx 는 8KB 상한(넘으면 413 — 앱에 닿지 않는 유일한 경우)과 `client_body_timeout 10s`(두 번의 읽기 사이 간격 — 전체 기한이 아니다)만 맡는다.
  - nginx 가 서버에서 여는 포트는 `.env` 의 `PUBLIC_PORT`(비면 18000)다 — 바꾸면 `docker compose up -d nginx` 로 nginx 를 다시 만들고, ci-cd agent 의 `DEPLOY_HEALTH_ADMIN` 도 같은 포트로 맞춘다. 자리 포트(18001·18002)와 컨테이너 안쪽 포트(18000)는 그대로다.
  - `deploy/active/` 는 서버에만 있고 git 에 없다. `edge-allow.conf` 가 없으면 nginx 가 뜨지 않는다(닫힌 쪽으로 실패).
  - 배포·전환·수동 조작은 ci-cd 저장소 README 의 "무중단 배포" 절을 따른다. 자리 포트: blue `127.0.0.1:18001`, green `127.0.0.1:18002`.
- 비밀번호 해시 만들기(한 줄 — 평문이 셸 기록에 남지 않게 읽어서 넣는다). **비용은 `m=19456,t=2,p=1` 로 고정**이다 — 설정 해시가 `$argon2id$v=19$m=19456,t=2,p=1$` 로 시작하지 않으면 더미 해시와 검증 시간이 달라지므로 설정 없음과 같다(서버가 뜨지 않는다 — 아래 "환경 변수"). 아래 명령은 그 매개변수를 명시한다:

  ```sh
  docker run --rm -it admin-app:local node -e 'const r=require("readline").createInterface({input:process.stdin,output:process.stderr});r.question("password: ",p=>{r.close();require("@node-rs/argon2").hash(p,{algorithm:2,memoryCost:19456,timeCost:2,parallelism:1}).then(h=>console.log(h))})'
  ```

- 세션 서명 키: `openssl rand -hex 32`.

- 배포된 컨테이너에서의 **값 검사**(빌드 때는 비밀값이 없어 이름만 검사한다): 컨테이너 안의 실제 환경 변수 값으로 브라우저로 가는 묶음을 검색한다. 값은 출력하지 않고 이름·파일만 알린다(8자보다 짧은 값은 이름만 알리고 건너뛴다). 하나라도 나오면 exit 1.

  ```sh
  docker exec admin-app-blue sh scripts/check-client-bundle.sh --env-values   # 활성 자리 이름으로
  ```

## 환경 변수

`.env.example` 에 키 이름과 설명.

- **필수**(하나라도 없거나 형식이 틀리면 **서버가 뜨지 않는다 — 종료 코드 78**): `ADMIN_USER` · `ADMIN_PASSWORD_HASH`(argon2id, 비용 `m=19456,t=2,p=1`, 검증 라이브러리가 실제로 읽을 수 있어야 함 — 시작 때 argon2 검증 1회로 확인, 약 50~70ms, 결과는 기억) · `SESSION_SECRET`(32자 이상) · `ADMIN_ORIGIN`(https 이고 출처 꼴 그대로 — `new URL(값).origin === 값`, 끝의 `/`·경로·scheme 없음은 틀림) · `OBSERVE_URL`(해석되는 http(s) 주소, 끝의 `/` 허용) · `OBSERVE_SECRET` · 화면 넷 · 잠금 알림이 부르는 서버의 `DEPLOY_MASTER_URL` · `BACKEND_URL` · `ALERT_URL`(셋 다 해석되는 http(s) 주소, 끝의 `/` 허용) · `DEPLOY_SECRET` · `ALERT_SECRET`(비지 않은 값). 서버가 뜰 때(`instrumentation.register()`) 검사해 빠진 키 **이름**만 1줄(`startup:admin:설정 없음 — 서버를 끝낸다 keys=…`) 남기고 종료 코드 78 로 끝낸다(값은 찍지 않는다). 빌드(`next build`)는 설정 없이 된다 — 검사는 서버가 실제로 뜰 때만.
  - 실측: 요청을 하나도 받기 전에 끝난다(컨테이너 안에서 시작 직후부터 헬스를 두드려도 응답 0건). `restart: unless-stopped` 아래에서는 재시작이 되풀이된다(12초에 5회).
  - 배포에서의 뜻: 새 자리가 뜨지 않으므로 compose healthcheck 는 healthy 가 되지 않고, ci-cd agent 의 자리 헬스 확인(`127.0.0.1:18001`/`18002`)이 실패해 그 배포는 `cd_health` 실패로 끝난다 — nginx 는 전환되지 않고 이전 자리가 계속 서비스한다.
  - 헬스(`GET /api/health`)도 필수 설정이 유효할 때만 200, 아니면 503(본문에 키 이름·값 없음) — 시작 검사가 건너뛰어져도 자리 헬스 확인에서 걸린다.
- **선택**: `LOG_REDIS_URL`(비면 stdout 만) — 비어 있으면 시작 로그에 이름만 1줄. `GITHUB_TOKEN`(배포 상세가 GitHub REST API 로 PR 제목 · 본문을 읽을 때 싣는 토큰 — 커밋 목록 · diff 는 GitHub 가 아니라 master 에서 읽는다) — 비면 토큰 없이 부른다(GitHub 익명 한도 IP 당 시간당 60회, 토큰이 있으면 5000회 — 한도를 넘으면 상세의 PR 구역만 "GitHub: 한도 초과"). 권한은 **공개 저장소 읽기 전용**만 준다(fine-grained token 의 "Public repositories (read-only)", 그 밖의 권한 없음). 값은 서버 쪽에만 있고 로그 · 응답 · 오류 문구에 나오지 않는다.
  `CLAUDE_RUNNER_URL`(Claude 실행 자리의 주소 — 해석되는 http(s), 끝의 `/` 허용) · `CLAUDE_RUNNER_SETTINGS_SECRET`(실행 자리의 **설정용** 비밀값 — 호출용 비밀값과 다른 값) — 비면 Claude 사용량 화면의 칸이 "설정 없음"이고 상한 바꾸기는 503(실행 자리가 배포되기 전에도 어드민이 뜬다 · 시작 검사에 넣지 않는다). 비밀값만 비면 헬스(인증 없음)는 읽는다.
  `CLAUDE_RUNNER_SECRET`(실행 자리의 **호출용** 비밀값 — 실행 자리의 것과 같은 값 · 설정용과 다른 값) — 비면(또는 `CLAUDE_RUNNER_URL` · `LOG_REDIS_URL` 이 비면) 문제의 분석은 "설정 없음"이고 보내기는 503.
  `OWNER_COOKIE_SECRET`(주인 표시의 서명 열쇠 — backend 와 같은 값 · UTF-8 32바이트 이상 · **글자 그대로** 쓴다, 앞뒤 공백도 열쇠의 일부) · `OWNER_COOKIE_DOMAIN`(쿠키의 Domain — 어드민과 사이트가 함께 속한 상위 도메인, `ADMIN_ORIGIN` 의 호스트가 그 도메인이거나 그 아래) — 하나라도 쓸 수 없으면 주인 표시 화면이 "설정 없음"이고 표시하기는 503(시작 검사에 넣지 않는다). 열쇠만 없고 도메인이 맞으면 지우기는 된다.

## 보안 경계 요약

- 비밀값(`X-Observe-Secret` · `X-Alert-Secret` · `X-Deploy-Secret` · `X-Claude-Runner-Settings-Secret` · 세션 서명 키 · 비밀번호 해시)은 서버 프로세스의 환경 변수에만 있다. 다른 서버 호출은 전부 서버 쪽 코드에서 한다.
- 세션: `admin_session` 쿠키(`HttpOnly; Secure; SameSite=Strict; Path=/`, 12시간). 쿠키만으로 판정하므로 로그아웃 전에 복사된 쿠키는 만료까지 유효하다(수용 — 전체 무효화 = `SESSION_SECRET` 교체). `Secure` 이므로 브라우저는 https(엣지)로만 쿠키를 보낸다.
- 로그인 · 로그아웃은 `Origin` 이 `ADMIN_ORIGIN` 과 글자까지 같을 때만 받는다. Server Action 은 쓰지 않는다.
- 잠금은 관측 서버가 판정한다(연속 5회 → 15분). 관측 서버에 닿지 않으면 자리 메모리의 임시 제한(3회 → 15분)으로 판정하고 화면에 "임시 제한 중"을 표시한다. 잠금이 시작되면(임시 제한 포함) 알림 서버에 이벤트 1건.
- 클라이언트 IP: nginx 가 **엣지 IP 와 사설 대역에서 온 연결만** 받고(나머지는 응답 없이 닫음), 앱에 넘기는 `X-Real-IP` 를 다시 쓴다 — 엣지에서 온 연결이면 엣지가 넣은 값, 아니면 실제 접속 주소. 앱은 `X-Real-IP` 하나만 읽고(`X-Forwarded-For` 는 보지 않는다), 없으면 `unknown` 한 통으로 센다.
- 보호 화면·데이터 응답은 요청마다 렌더링하고 `Cache-Control: no-store`.
- 판정 순서: Origin 검사 → 속도 제한 → 본문 읽기 → 자격 검증. 본문은 앞의 두 검사를 통과한 뒤에만 읽고, 읽으면서 상한 4KB·기한 3초를 적용한다(넘으면 400 `malformed`). 형식이 틀린 본문도 속도 제한에 센다(Origin 거절은 세지 않는다).
- 관측 판정은 첫 호출과 재시도를 합쳐 기한 5초 하나다 — 연결 실패·2xx 아님·해석 불가만 같은 `attempt_id` 로 남은 시간 안에서 1회 재시도하고, 시간 초과는 재시도하지 않는다. 기한이 지나면 임시 제한으로 판정한다(관측 서버가 느려도 로그인은 약 5초에 끝난다).
- 속도 제한 표(IP 상한 10,000): 창 안의 IP 는 지우지 않는다. 표가 활성 항목으로 가득 차면 새 IP 는 429(관측 서버에 기록하지 않고 건수만 앱 로그), 창이 지난 항목은 정리한다.
- 대기열의 주기 재전송: 대기열이 비어 있지 않은 동안 30초마다 스스로 재전송한다(관측 서버가 돌아오면 다음 로그인을 기다리지 않는다). 재전송은 한 번에 하나만 돌고(로그인 뒤 실행과 겹치지 않는다), 도는 중에 들어온 항목도 같은 실행 또는 다음 시도에서 보낸다. 관측 호출의 5초 기한을 따르고, 타이머는 프로세스 종료를 막지 않는다(`unref`). 비면 멈춘다.
- 집계 로그: 관측 서버에 보내지 않는 거절(창 안의 반복 Origin 거절 · 형식 오류 · 속도 제한, 그리고 표 포화 `saturated`)은 요청마다 로그를 남기지 않고 이유별 60초에 1줄(`login:unrecorded_rejections reason=<이유> count=<n>`)로 남긴다. 창이 끝날 때와 종료(SIGTERM) 때 남은 건수를 내보낸다. 0 건이면 줄이 없다.
- "임시 제한 중" 표시: 마지막 관측 호출이 실패했거나 대기열에 항목이 있는 동안 로그인 화면과 로그인 뒤의 모든 화면(공통 틀)에 표시한다.
- 시도 기록: 자격 검증에 이른 요청은 `/auth/attempts`, 그 전에 거절한 요청은 `/auth/attempts/rejected`(`reason` = `rate_limited` · `origin_rejected` · `malformed`). 거절 기록은 IP 마다 고정 60초 창에 이유별 첫 1건만 보내고(꾸준히 두드려도 1건) 나머지는 건수만 앱 로그에 남긴다. 403·400·429 응답은 기록 전송을 기다리지 않는다 — 전송은 뒤에서 끝까지 하고 실패하면 대기열에 넣는다. 관측 서버 장애 중의 기록은 대기열에 두었다가 복귀 뒤 `replayed:true` + 임시 제한이 실제로 내린 `outcome` 으로 보낸다. 재전송 응답이 잠금 시작이면 그때 알림을 보낸다. 재전송에 관측 서버가 **422**(본문 자체가 틀림)를 준 항목만 버리고 `discarded=<건수> status=422` 를 앱 로그에 남긴다 — 401·429·5xx·연결 실패·시간 초과는 남겨 다음에 다시 보낸다. 관측 서버가 허용한 성공은 임시 제한의 메모리 횟수도 0 으로 만든다. 알림은 로그인 응답을 최대 2초만 기다린다.
- 종료 로그: 대기열에 넣을 때마다 `queued=<건수>`, SIGTERM 을 받으면 `login:shutdown queued=<대기 건수> dropped=<누적 유실 건수>` 1줄. 종료 자체는 Next 서버의 SIGTERM 처리(연결 정리 뒤 종료)가 한다. 강제 종료(SIGKILL) 때는 마지막 `queued=` 줄이 근사값이다.

## 재배포 접수

버전 목록(`/deploys/versions`)에서 버전을 고르면 확인 화면(`/deploys/redeploy?service=&commit=`)이 지금 버전 → 고른 버전과 그 사이의 커밋을 보이고, 비밀번호를 다시 넣는 폼으로 배포 master 에 접수한다(`POST /api/deploys/redeploy` — 어드민에서 운영을 바꾸는 유일한 경로). 폼은 스크립트 없이 보낸다.

- 검사의 차례(앞 단계가 거절하면 뒤 단계의 호출이 없다): 배포된 서버에서는 세션이 없으면 middleware 가 먼저 401 JSON 을 낸다(로그아웃과 같은 구조). route 안의 차례는 출처(`Origin` 이 `ADMIN_ORIGIN` 과 글자까지 같음 — 403 JSON) → 세션(401 JSON) → 속도 제한(계정당 60초에 5번 — 자리마다 따로 센다) → 입력의 꼴(urlencoded · 4KB · 칸마다 하나 · 커밋은 소문자 40자) → 계정 이름(`admin:<ADMIN_USER>` 가 `^[A-Za-z0-9._:-]{1,128}$` 안 — 계정은 `[A-Za-z0-9._-]`) → 확인 값(서비스 · 커밋 · 요청 ID · 만든 시각 · 계정에 세션 서명 키로 서명, 5분 안에만, 상태 없음) → 비밀번호(로그인과 같은 흐름 — 잠금 판정 · 시도 기록 · 관측 서버 장애 때의 임시 제한. 틀린 입력은 로그인의 잠금 횟수에 든다. 세션 쿠키는 새로 놓지 않는다) → 이력 재확인(그 서비스의 성공한 배포 이력 최근 200건에 있는 커밋만 — 배포 이력만 읽고 git 조회는 하지 않는다) → master `POST /deploy` 한 번(본문 `requested_by: admin:<계정>`, 기한 10초, 다시 보내지 않는다).
- 결과: 접수됨 · 같은 요청의 재접수 → 배포 이력의 그 배포 상세로 303 / 진행 중 409 / master 가 받지 않음 · 연결을 맺지 못함 · 5xx 502 / 접수 여부 모름 504(10초 기한 · 보낸 뒤 연결이 끊김 · 모르는 실패 — 같은 확인 값으로 다시 보내는 폼 — 같은 요청 ID 라 master 가 같은 배포로 답한다) / 확인 값 만료 410. 출처 · 세션 밖의 실패는 HTML.
- 설정: **새 환경 변수는 없다** — `DEPLOY_MASTER_URL` · `DEPLOY_SECRET`(접수도 같은 비밀값) · `SESSION_SECRET`(확인 값의 서명 키) · `ADMIN_USER` · `ADMIN_PASSWORD_HASH` · `OBSERVE_*` 를 그대로 쓴다.
- 올리는 순서: **master(ci-cd)를 먼저** `requested_by` 를 받는 판으로 올린 뒤 어드민을 올린다. 옛 master 는 `requested_by` 를 조용히 무시해 접수를 `github` 로 기록하고 접수 알림도 보내지 않는다.
- **master 를 옛 판으로 되돌릴 때는 어드민의 접수도 함께 내린다**(어드민을 앞 판으로 되돌리거나 확인 화면을 쓰지 않는다) — 위와 같은 까닭으로 누가 일으켰는지가 사라진다.
- 로그: 접수 한 건에 한 줄 `redeploy:<결과> service=… commit=<7자> account=…`. 비밀번호 · 확인 값 · 비밀값은 로그 · 응답 · 주소에 없다.
- **문제의 조치**(⑫ 12-6 — 같은 길이다, 새 접수 길은 없다): 문제 화면의 근거 묶음의 "조치" 구역이 조치마다 확인 화면으로 가는 **링크**(`/deploys/redeploy?service=<서비스>&incident=<문제의 ID>&action=redeploy|rollback` — `commit` 을 싣지 않고, 실어 보내면 입력 거절)를 둔다. 서비스는 문제의 근거에서 하나로 정해질 때만(감시 대상은 대응 표 · 배포 실패 · 오류 로그는 그 서비스 · 자원 임계값은 그 서버에서 찾은 서비스가 하나일 때) — 아니면 링크 대신 까닭.
  - 확인 화면은 **그 순간** 문제를 다시 찾고(닫힘 · 확인하지 못함이면 확인 화면 대신 까닭) · 문제의 서비스와 주소의 서비스가 같은지 보고 · 판을 그 서비스의 배포 이력(버전 목록과 같은 출처)에서 다시 정한다: 다시 배포 = 지금 판(가장 최근 성공 배포) · 되돌리기 = 지금 판 바로 앞의 성공 배포(그것이 지금과 같은 판이면 더 옛 판으로 건너가지 않고 까닭). 그 뒤는 위의 확인 화면 그대로에 "문제 <ID> 의 조치" 한 줄과 문제 화면으로 돌아가는 링크.
  - 확인 값은 문제의 ID 가 있을 때만 서명에 여덟째 줄 `incident:<ID>` 와 아홉째 줄 `action:<redeploy|rollback>` 을 더한다(없으면 지금의 값과 글자까지 같다) — 폼의 숨은 칸 `incident` · `action` 은 함께만 오고, 확인 화면과 접수 사이에 바꾸거나 빼거나 더하면 400. 비밀번호 · 한 번만 · 속도 제한은 그대로다.
  - **접수 직전에 다시 정한다**(문제에서 온 접수만): 확인 값 다음 · 비밀번호 전에 확인 화면과 같은 판정으로 그 순간의 판을 다시 정해, 서명한 판과 다르거나 정할 수 없으면 접수하지 않고 **409** "그 사이 배포나 문제의 상태가 바뀌었습니다 — 문제 화면에서 다시 확인하세요"(비밀번호를 보지 않아 잠금 횟수에 들지 않는다 · 배포 서버를 부르지 않는다). 로그 `redeploy:incident_changed reason=<낱말> service=… commit=<7자> account=… incident=<ID>` — 낱말: `target_changed`(판이 바뀌었거나 정할 수 없음) · `incident_closed` · `incident_unchecked` · `service_changed`(서비스를 정할 수 없거나 달라짐) · `history_unavailable`(그 서비스의 이력을 읽지 못함). 버전 목록에서 온 접수는 다시 정하지 않는다(고른 판으로 간다). 다시 정하기는 **필요한 것만 읽는다** — 그 문제를 가르는 목록의 출처 하나(감시 대상 DOWN = 알림 `/monitors` · 배포 실패 = 배포 서버 `/deploys` · 오류 로그 = 관측 `/logs` 의 오류 검색 · 자원 임계값 = 관측 `/metrics/latest` — 그 서버의 서비스도 여기서)와 그 서비스의 이력 `/deploys?service=&limit=200` 하나(확인 화면도 같은 판정). 전체에 **기한 8초**(절대 — 넘으면 409 와 까닭 "상태를 제때 확인하지 못했습니다" · 로그 낱말 `recheck_timeout` · 늦게 끝난 결과는 버린다 · 비밀번호 확인 · 접수 0). 문제에서 온 접수의 가장 긴 합은 다시 정하기 8초 + 관측 판정 5초 + 이력 재확인 5초 + 접수 10초 = 28초로 nginx 의 `proxy_read_timeout 30s` 아래다(여유 2초 — argon2 의 비밀번호 계산 시간은 기한 상수가 없어 이 합에 들지 않는다는 한계). 다시 정한 뒤 접수까지(평소 1초 미만)에 배포가 끼면 서명한 판으로 간다(받아들인 창).
  - 실패 화면의 "확인 화면으로 돌아가기"는 문제에서 온 접수면 문제의 확인 화면(`service` + `incident` + `action` — 판은 다시 정한다)으로 간다. 결과 로그 줄 끝에 ` incident=<ID>`(문제에서 온 것만).
  - **누가의 꼴**: 문제에서 온 접수의 `requested_by` 는 `admin:<계정>:incident:<문제의 ID>`(그 밖은 `admin:<계정>` 그대로). master(ci-cd)는 `^[A-Za-z0-9._:-]{1,128}$` 를 검사하므로 문제의 ID(최대 64자)를 더해 128자를 넘으면 **문제에서 접수할 수 없다**(계정 이름이 긴 경우 — 확인 화면에 그 까닭, 접수는 422). 접수됨 303 은 배포 이력의 그 배포 + `&incident=<ID>`(배포 이력 화면에 "문제 <ID> 화면으로" 링크).
  - 문제 화면의 판과 "이 문제에서 접수한 조치"(요청한 사람이 정확히 `admin:<계정>:incident:<이 ID>` 인 배포)는 **그 서비스의 배포 이력**(`/deploys?service=<서비스>&limit=200` — 확인 화면과 같은 출처 · 서비스가 정해질 때만 호출 하나 더 · 읽지 못하면 까닭)에서 정한다 — 목록의 모든 서비스 최근 200건에서 정하지 않는다. 같은 발생의 가장 최근 끝난 분석이 되돌리기 · 다시 배포를 권했으면 그 줄에 "Claude 가 권함"(표시일 뿐 — 링크는 같다). 새 저장은 없다.
- **배포 서비스 목록**(이력 · 버전 · 상세 · 재배포 · 문제의 조치가 함께 쓴다 — ci-cd master 의 고정 열거와 같은 일곱): `front` · `backend` · `llm` · `alert` · `observe` · `admin` · `claude`(Claude 실행 자리 — 저장소 `study-note-deploy-system-claude`). `claude` 는 단일 컨테이너라 다시 배포 · 되돌리기 동안 몇 초 답하지 않는다(그동안 Claude 를 부르는 쪽은 실패를 받는다). 지금의 한계: 실행 자리의 로그 서비스 이름은 `claude-runner` 라 상태 화면의 로그 링크(`service=claude`)는 빈 결과가 된다.

## 문제의 분석

문제 화면의 근거 묶음에서 "분석"으로 간다. Claude 가 원인 · 근거 · 확신의 정도 · 대처법 · 권하는 조치를 답하고, 그 답과 보낸 글이 저장돼 다시 열면 보인다(다시 부르지 않는다 — "다시 분석"은 사람이 누른다). 시작은 **사람이 누를 때만**이다(자동 시작은 없다).
- **두 걸음**: ① `/incidents/analysis?incident=<id>&preview=1` 이 **보낼 글 그대로**(가린 뒤 · 자른 뒤의 최종 글과 바이트 · 자 수 · 줄인 것 · 가린 것의 수)를 보인다 — 실행 자리를 부르지 않고 저장하지 않는다. ② "이 글을 보낸다"(폼 POST)가 **미리본 글 그대로**를 보낸다 — 다시 만들지 않는다(미리보기가 글의 SHA-256 · 문제 · 그 문제의 "언제부터" · 계정 · 시각에 세션 서명 키로 서명한 값 `ap2` 를 싣고, 글이 한 바이트라도 다르거나 다른 문제 · 10분이 지났으면 409 · 미리본 뒤 같은 식별자가 다른 "언제부터"로 다시 열렸으면 409). **미리보기 하나는 한 번만 보낸다** — 쓴 서명 값의 해시를 Redis 에 10분 동안 적어 두고(`SET NX`) 같은 폼을 다시 보내면 409("다시 분석"은 미리보기를 다시 열어서). 브라우저가 폼의 줄바꿈을 CRLF 로 바꿔 보내는 것은 되돌린 뒤 견준다. 보내기의 차례: 출처(403) → 세션(401) → 본문(urlencoded · 1MB · 칸마다 하나 — 400) → 서명(400 · 409) → 설정(503) → 문제가 아직 열려 있는가(목록의 네 호출 — 닫힘 · 확인하지 못함 409) → 같은 발생분인가(409) → 쓴 미리보기인가(409 · 저장소에 닿지 못하면 503) → 시작(저장소에 닿지 못하면 503 — **실행 자리를 부르지 않는다**) → 303 분석 화면.
- **무엇이 밖으로 나가는가**: 보내는 곳은 Claude 실행 자리(`POST /runs` 용도 `analysis` — 그 뒤 Anthropic). 글 = 고정 지시문 + 매번 새로 뽑은 무작위 표지(16진 32자 — 자료에 그 글자가 있으면 다시 뽑는다) 사이의 자료 + 고정 끝맺음. 자료 = 문제 화면의 근거 묶음(관련 알림 · 로그의 글 · 배포 · 자원 · 무엇이)과, 배포 실패면 배포 마스터가 남긴 실패한 단계의 전체 출력(`GET /deploys/<요청 ID>/output` — 가린 뒤 16,000바이트 안에서 끝부분 먼저). 자료는 모두 48,000바이트 안이고 글은 6만 자 안이다. 실행 자리 쪽의 Claude 에게는 도구가 없다 — 자료에 지시가 심겨 있어도 아무것도 실행되지 않는다.
- **가리기 전에 글자를 정리한다**(배포 마스터의 글자 정리와 같게): ANSI 색 코드 · OSC 를 지우고, CR 을 줄바꿈으로, 탭 · 줄바꿈 밖의 제어 문자 · 줄 구분(U+2028 · U+2029) · 글의 방향을 바꾸는 서식 문자를 U+FFFD 로 바꾼다 — 색 코드가 이름과 값 사이에 끼어 가림을 비껴가지 못하고, 미리보기에 보이는 글이 보내는 바이트와 같다.
- **가림은 한 겹 더일 뿐이다**: 보내기 전에 어드민이 키 꼴 · 토큰 · `Authorization` · URL 의 자격 · 비밀 칸(이름이 password · secret · token · api_key 류로 끝나는 칸) · 41자 넘는 16진 · 메일 · 내부 주소를 `[가림:<종류>]` 로 바꾼다(배포 마스터가 이미 가린 것은 그대로). 꼴로 찾는 것이라 모든 비밀값을 잡지 못한다 — 1차는 로그에 비밀값을 찍지 않는 규약이다. 미리보기에서 보낼 글을 사람이 보고 보낸다.
- **저장**: 어드민의 Redis(`LOG_REDIS_URL` — 새 저장소 없음). 문제마다 최근 5건 · 30일 — 보낸 글 그대로 · 보낸 시각 · 걸린 시간 · 답의 다섯 칸 또는 실패의 까닭 · 그 문제가 언제부터 열린 것이었나(닫혔다 다시 열린 뒤면 "옛 분석") · 누른 사람. 같은 문제는 한 번에 하나만 돈다(`SET NX PX` 5분 잠금 — 두 자리가 함께 받아도 한 번). 보내기는 곧바로 "진행 중"으로 답하고 실행 자리는 뒤에서 부른다(기한 260초) — 화면은 진행 중일 때만 5초마다 다시 읽는다. 프로세스가 도중에 죽거나 저장하지 못하면 5분 뒤 "끊김 — 결과를 모름"으로 보인다(실행 자리는 한 번을 셌을 수 있다). 종료(SIGTERM) 때 도는 분석의 수를 로그 한 줄로 남긴다.
- **보이기**: 답은 글로만(마크다운 · HTML 을 풀지 않고 링크로 만들지 않는다 · 제어 · 서식 문자를 지운다). 권하는 조치는 표시일 뿐 누를 것이 없다. 어드민도 답의 꼴을 한 번 더 검증한다(틀리면 저장하지 않는다). 실행 자리의 실패(상한 · 바쁨 · 꺼짐 · 토큰 없음 · 답의 꼴 등)는 저마다 다른 고정 글 — 실행 자리의 글 · 주소는 화면 · 로그에 내지 않는다.
- 로그: 한 번에 한 줄 `incident-analysis:<결과> …`(요청 ID · 문제 식별자 · 걸린 시간 · 바이트 수만) — 보낸 글 · 답의 내용은 로그에 없다(저장소의 시도 기록에만).
- nginx: 분석 요청의 본문은 수백 KB 가 될 수 있어 `location = /api/incidents/analysis` 만 `client_max_body_size 1m`(앱의 본문 상한과 같다 — 서버의 16k · 로그인의 8k 는 그대로).
- 멈출 때의 줄 확인: `npm run build && sh scripts/check-shutdown-lines.sh` — 가짜 설정으로 standalone 의 `node server.js` 를 직접 띄워 SIGTERM 을 보내고 `login:shutdown` · `incident-analysis:shutdown` 이 한 번씩 나오는지 본다(신호는 npx · 셸이 아니라 node 에 직접 보내야 한다).
- 알려진 한계: **가림 규칙과 글자 정리가 배포 마스터(Go — ci-cd `internal/shared/failure_output.go`)와 어드민(TypeScript — `lib/analysis-masking.ts`)에 두 벌이다 — 한쪽을 고치면 다른 쪽도 고친다.** 실행 자리의 사용 상한이 정본이다(어드민은 따로 세지 않는다). 분석 한 번이 도는 동안(240초까지) 실행 자리는 채팅을 받지 않는다(동시에 한 건).

## Claude 사용량

`/claude-usage` 는 Claude 실행 자리(`study-note-deploy-system-claude`)의 상태 · 사용량 · 최근 호출 · 상한을 보이고, 상한 · 켬/끔을 바꾸는 폼을 둔다(`GET /api/claude-usage` 는 같은 데이터의 JSON). 브라우저는 실행 자리를 부르지 않는다 — 어드민 서버가 세션을 확인한 뒤에만 `CLAUDE_RUNNER_URL` 로 부르고, 설정용 비밀값은 머리글 `X-Claude-Runner-Settings-Secret` 으로만 싣는다(헬스에는 싣지 않는다).

- 칸 넷: 실행 자리 상태(`GET /health` — 정상 · 구독 토큰 없음 · `claude` 실행 파일 없음 · 장부를 쓸 수 없음) · 사용량(`GET /usage` — 전체와 용도마다 오늘(서울 자정부터) · 최근 한 시간의 "건수 / 상한"과 여유 · 상한에 닿음 · 꺼짐) · 최근 호출(같은 응답의 `recent`) · 상한(`GET /limits` — 켬/끔 · 마지막으로 바꾼 사람과 시각 · 폼). 한 칸을 읽지 못하면 그 칸만 "지금 읽지 못했습니다 — <고정 사유>"이고 0 으로 메우지 않는다(표 · 폼을 그리지 않는다). 세 호출은 병렬 · 각각 5초.
- 용도의 목록은 어드민에 박지 않는다 — 실행 자리의 응답에서 온다(이름의 꼴 `^[a-z][a-z0-9_]{0,31}$` · 1~8개 · 중복 없음만 검사, 벗어나면 그 칸은 "해석 불가"). 알려진 이름(`chat`)은 "채팅 (chat)", 모르는 이름은 이름 그대로 보인다 — 실행 자리에 용도가 더해져도 어드민을 함께 배포하지 않는다.
- 바꾸기(`POST /api/claude-usage/limits` — 폼, 스크립트 없음)의 차례: 출처(403 JSON) → 세션(401 JSON) → 본문의 꼴(urlencoded · 4KB · UTF-8 — 400) → 계정 이름(`admin:<ADMIN_USER>` 로 쓸 수 있는가 — 422) → 설정(503) → **지금 상한을 서버가 다시 읽는다**(읽지 못하면 바꾸지 않는다 — 503) → 폼의 칸(지금 상한의 용도마다 두 칸 · 0~1000 의 정수 · 선택 칸 `confirmation` — 빠지거나 남는 칸 400(폼이 보낸 "앞 값" 칸 포함), 틀린 값 422) → **넓힘의 판정** → 실행 자리 `PUT /limits` 한 번(기한 10초 · `changed_by` 는 서버가 정한 `admin:<계정>`).
- **넓히는 바꿈은 두 걸음**(재배포 접수와 같은 꼴): 넓힘 = 꺼 둔 것을 켬 · 전체나 어느 용도의 하루 · 한 시간 상한이 하나라도 **실행 자리가 지금 쥔 값**(바꾸기 직전에 다시 읽은 값 — 폼을 믿지 않는다)보다 커짐. 내리기만 하거나 끄는 바꿈은 확인 없이 곧바로 바꾼다(확인 값 · 비밀번호가 와도 보지 않는다).
  1. 첫 걸음: 확인 화면 200 — 지금 → 새 값의 표 · 켬/끔 · 숨은 칸(새 값 전부와 확인 값) · 비밀번호 칸. 비밀번호를 함께 보내도 이 걸음에서는 보지 않는다.
  2. 둘째 걸음: 확인 값 → 비밀번호(로그인과 같은 흐름: 잠금 판정 · 시도 기록 · 임시 제한 — 틀리면 로그인의 잠금 횟수에 든다, 세션 쿠키는 놓지 않는다) → PUT 한 번. 확인 값이 틀리면 비밀번호를 보지 않는다: 꼴이 아님 400 · 그 사이 값이 달라짐 409 · 5분 지남 410(둘 다 새 지금 값으로 만든 새 확인 화면). 빈 · 틀린 비밀번호 401(같은 확인 값의 폼) · 잠김 423 · 잦음 429.
  - 확인 값 `cc1.<만든 시각>.<서명>` — 세션 서명 키의 HMAC-SHA256 으로 계정 · 만든 시각 · 앞 값의 바꾼 시각(`changed_at`) · 앞 값 · 새 값 전부를 묶는다(값 · 계정은 싣지 않는다, 상태 없음, 5분). 앞 값의 바꾼 시각을 묶어 넓힌 뒤 누가 같은 값으로 되돌려도 같은 확인 값으로 다시 넓히지 못한다. 용도 줄이 달라 재배포의 확인 값 · 세션 토큰과 서로 바꿔 끼워지지 않는다.
- 결과(HTML): 바뀜 200(실행 자리가 돌려준 값) · 실행 자리가 값을 거절 422 · 설정 비밀값 거절 502 · 연결을 맺지 못함 502(바뀌지 않음 — 요청이 나가지 않았다고 말할 수 있을 때만) · **모름 504**(5xx · 기한 초과 · 보낸 뒤 끊김 — 실행 자리는 값을 쓴 뒤에도 5xx 를 낼 수 있다. 다시 보내지 않는다. 화면을 다시 열어 확인).
- 로그: 한 번에 한 줄 `claude-limits:<결과> account=<계정> raise=<true|false|->`(올림인지 아직 모르는 단계의 거절은 `-` · 첫 걸음은 `confirmation_required`). 넓히는 바꿈의 PUT 결과 줄에만 ` from=<앞 값> to=<새 값>`(예 `on;total=30/10;chat=30/10` — 누가 무엇을 얼마에서 얼마로, 알림 서버에 보내는 사건은 아직 없다). 비밀번호 · 확인 값 · 비밀값 · 실행 자리의 주소는 로그 · 응답에 없다.

## 주인 표시

`/owner-mark` 는 로그인한 사람이 지금 쓰는 브라우저를 사이트의 **주인**으로 표시하거나 그 표시를 지우는 화면이다. 주인으로 표시된 브라우저에서만 사이트(front · backend)가 Claude 대체 답변과 실습을 연다 — 판정은 backend 가 이 쿠키로 한다(명세 §17 2a).

- 무엇: 서명한 쿠키 `study_owner=ow1.<만든 시각 ms>.<서명>` — 서명 = HMAC-SHA256(`OWNER_COOKIE_SECRET` 의 UTF-8 바이트, `study-owner` LF `ow1` LF `<만든 시각>`)의 base64url 43자. 속성 `Domain=<OWNER_COOKIE_DOMAIN>; Path=/; Max-Age=2592000(30일); Secure; HttpOnly; SameSite=Lax`. 값 · 시각 · 도메인은 설정과 서버의 시계에서만 — 요청의 몸 · 질의 · Host 는 보지 않는다.
- 전제: 어드민과 사이트가 **같은 상위 도메인**을 쓴다(어드민의 응답이 그 도메인에 쿠키를 심는다 — `ADMIN_ORIGIN` 의 호스트가 그 도메인 밖이면 브라우저가 쿠키를 버리므로 "설정 없음"). 엣지 · nginx 가 `Cookie` 를 backend 까지 넘긴다.
- 차례(`POST /api/owner-mark` 심기 · `POST /api/owner-mark/clear` 지우기 — 폼, 스크립트 없음): 출처(403 JSON) → 세션(401 JSON) → 속도 제한(계정당 60초에 5번 · 심기와 지우기를 함께 — 429) → 설정(503 "설정 없음" + 확인할 환경 변수의 이름) → `Set-Cookie` + 303 `/owner-mark`. 화면은 이 브라우저의 상태(주인 · 만든 날 · 끝나는 날 / 표시 없음 / 쓸 수 없음과 까닭의 낱말)를 backend 와 같은 규칙으로 보인다. 쿠키의 값 · 서명은 화면 · 응답 · 로그에 없다.
- 조용히 "표시 없음"으로 남는 경우: `OWNER_COOKIE_DOMAIN` 이 공개 접미사(`co.kr` · `github.io` 류)면 설정 검사는 통과하고 303 과 `Set-Cookie` 가 나가지만 브라우저가 쿠키를 버린다(공개 접미사 목록은 들이지 않았다). 브라우저가 쿠키를 막아도 같다. 그래서 설정이 맞는데 "표시 없음"이면 화면이 이 까닭의 후보를 한 줄로 보인다.
- 열쇠는 **ASCII 를 권한다** — backend 의 JVM 은 환경 변수를 컨테이너 로케일의 인코딩으로 풀고 어드민의 Node 는 UTF-8 로 푼다(여러 바이트 글자는 로케일에 따라 서명이 어긋날 수 있다). "공백뿐"의 판정이 두 쪽에서 다른 글자(U+FEFF 류)가 있으나, 어긋나도 닫힌 쪽(주인 아님)으로만 갈린다.
- 화면의 판정은 **어드민에 온 쿠키만** 본다 — 사이트 호스트에만 붙은 같은 이름의 쿠키는 어드민에 오지 않는다(사이트의 판정은 backend 의 `GET /api/owner` 가 정본). 날 `Cookie` 머리글에서 이름이 정확히 `study_owner` 인 조각을 직접 세어(Next 의 쿠키 읽기는 같은 이름이면 마지막 값 하나만 준다) 같은 이름의 쿠키가 둘이면 화면도 backend 처럼 `malformed` 다.
- 되돌리는 법: 그 브라우저에서 "주인 표시 지우기"(같은 이름 · Domain · Path 에 `Max-Age=0`) · 모든 표시를 한꺼번에 없애려면 `OWNER_COOKIE_SECRET` 을 바꾼다(어드민과 backend 를 함께).
- 로그: 한 번에 한 줄 `owner-mark:<set|cleared|origin_rejected|unauthenticated|rate_limited|not_configured> action=<set|clear> account=<계정>`(`not_configured` 는 뒤에 ` problems=<secret_unusable|domain_invalid|admin_outside_domain,…>`).
